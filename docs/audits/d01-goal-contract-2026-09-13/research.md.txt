## Architecture — 보존 불변식과 작은 접점

### 데이터·소유권

- 회차는 `Chapter.project_id`로 작품에 속한다. 현재 회차 상세 경로는 `/chapters/{cid}`이며, 작품 ID를 추가로 받는 새 계약은 반드시 실제 소속을 대조해야 한다.
- 기존 AI context는 작품/회차/장면의 교차 소속을 검증하고 원문 revision 불일치는 409로 거절한다(`ai_context.py:449–471`). 이를 변경하거나 새 사용자 계정/권한 체계를 도입할 범위가 아니다.
- 목표 저장이 원문 변경으로 취급되어 `Chapter.revision`을 증가시키거나 manuscript snapshot을 만들면 기존 CAS·stale 의미가 바뀐다. 최소안에서는 두 버전을 분리하는 편이 안전하다.
- 원문 복원은 같은 회차 snapshot만 허용하고, 과거 revision 번호로 되돌리지 않고 현재 원문을 다시 저장하는 경로다(`projects.py:257–269`, `manuscripts.py:54–114`). **목표 복원까지 자동으로 포함한다고 해석할 근거는 없다.**
- 회차 삭제는 SQLite writer lock 아래 복선/기억 참조를 검사하며 retired 기억도 삭제를 막는다(`projects.py:275–300`). D01이 이 정책을 우회해서는 안 된다.

### API·UI·cache

- 최소 연결점은 목표 전용 schema/read-write 경로, typed frontend 응답, 기존 브리프 폼의 load/save 경계다. Chapter metadata PATCH 전체를 재설계할 필요는 없다.
- 기존 query key는 상세 `['chapter', chapterId]`, 목록 `['chapters', pid]`이며 명시적인 typed cache 갱신을 사용한다(`EditorPage.tsx:159–168,315–334`). 목표 전용 key를 쓰면 원문 전체 응답이 목표 편집값을 덮는 결합을 줄일 수 있다.
- 모든 저장 요청에는 **요청 당시 작품·회차 식별자**를 고정하고 늦은 응답이 다른 회차의 폼/cache/toast를 변경하지 않게 해야 한다. 완료된 M01/M02를 다시 구현하는 것이 아니라 같은 경계 원칙을 새 목표 폼에 적용한다.
- 목표 로딩 실패를 빈 목표로 해석하지 않고, 저장 실패·409 시 입력을 유지해야 한다.
- 생성 시작 시 선택한 브리프를 동결하는 기존 흐름과 원문 flush/revision 경계를 유지한다(`AiPanel.tsx:265–355`). 서버가 요청 브리프를 몰래 다른 “최신 목표”로 바꾸는 방식은 별도 결정 없이는 금물이다.

## 저장 전략 비교

**아래는 승인된 schema/API 결정이 아닌 후보 비교다.**

| 후보 | 재사용 패턴·장점 | 한계 |
|---|---|---|
| A. Chapter에 목표 JSON·독립 버전·원문 기준 revision 추가 | 기존 Chapter/JSON/Alembic 패턴. 테이블 수가 적고 현재값 복원이 단순 | 원문 상세 응답·metadata 갱신과 결합. 과거 목표 내용은 복원 불가 |
| **B. 회차당 현재 목표 1행의 별도 테이블** | FK·unique·timestamp·JSON 패턴 재사용. 목표 CAS와 query를 원문에서 분리 | migration/table이 하나 필요. 역시 이력 요구가 있으면 추가 설계 필요 |
| C. 회차별 append-only 목표 버전 테이블 | ChapterSnapshot의 버전 보존 패턴 응용. 과거 목표·원문 근거 연결을 명확히 유지 | 목록/선택/복원/삭제 정책까지 늘어나므로 D01 최소 범위를 넘기기 쉬움 |

**권장 MINIMAL: B**, 단 “버전 연결”이 **현재 목표의 독립 버전과 작성 기준 원문 revision 기록**을 뜻한다는 소유자 확인이 선행되어야 한다. 프로젝트 소속은 회차 FK에서 도출하고, 저장은 기존 버전 조건부 갱신을 응용한다. 목표 저장으로 원문 revision은 변경하지 않는다.

과거 시점의 목표 내용까지 다시 볼 수 있어야 한다면 B를 완료로 주장할 수 없으며 C 또는 작은 목표 이력 계층이 필요하다. `memo`에 JSON을 덮어쓰는 방식은 기존 사용자 메모와 계약을 훼손하므로 권장하지 않는다.

## 상세 명세 전에 필요한 소유자 결정

질문은 다음 네 묶음으로 제한하는 것이 적절하다.

1. **소유 단위와 “버전 연결”의 의미**
   - 제안 기본값: 회차당 목표 하나, 작품은 상위 소속. 목표 버전과 작성 기준 원문 revision은 별개.
   - 확인: 작품 자체의 공통 목표도 필요한가? 과거 목표 내용 조회/복원까지 D01 필수인가?
   - 후자가 필수면 최소 저장 전략이 바뀐다.

2. **저장·재진입·원문 복원**
   - 제안 기본값: 명시적 목표 저장, 성공한 서버 값만 재시작 복원. 실패한 입력은 현재 화면에 유지. 원문 과거본 복원은 목표를 변경하지 않고 기준 revision 차이만 안내.
   - 자동저장이 필수라면 큐·충돌·이탈 중 미저장 보존까지 별도 명세가 필요하다.
   - 목표 과거본 복원도 원한다면 “새 목표 버전 생성”으로 처리할지 확정해야 한다.

3. **부분 입력과 생성에 사용할 값**
   - 제안 기본값: 빈/부분 목표는 저장 가능하되 기존 EpisodeBrief 생성 검증은 유지. 저장 상태와 생성 적용 가능 상태를 구분.
   - 확인: 생성 시 미저장 폼을 기존처럼 사용하는가, 마지막 저장본만 사용하는가? 최소 호환은 기존 폼 동결 경로 유지와 저장 여부 표시다.
   - 목적별 요구 조건·완료된 purpose 계약 자체는 재정의하지 않는다.

4. **목표 비우기·삭제**
   - 제안 기본값: 명시적 “목표 비우기”와 확인, 사용자 memo 보존. 회차 삭제는 기존 참조 차단 정책을 그대로 따른다.
   - 목표 이력/향후 D03 근거 참조가 있다면 hard delete 대신 보존해야 하는지 확정 필요.
   - **목표를 저장했다는 사실은 목표 달성·회차 완료의 증거가 아니다.** 자동 달성 판정·완결 분류는 D01에 포함하지 않는다.
