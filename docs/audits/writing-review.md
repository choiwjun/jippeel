# 집필 엔진·장편 연속성 감사

## 범위와 판정 기준

- 현재 작업 트리의 `backend/app/routers/ai_panel.py`, `services/{bootstrap,injection,semantic,parallel_writer,canon,quality}.py`와 관련 스키마·모델·평가 스크립트를 읽었다. 과거 HANDOFF는 검증 근거로 쓰지 않았다.
- 구현·실사용 DB를 수정하지 않았다. 외부·유료 LLM 호출과 전체 테스트 실행도 하지 않았다.
- 프로젝트의 Windows 가상환경 `.venv/Scripts/python.exe -B -c <재현 코드>`로 확인했다. import 전에 `DATABASE_URL=sqlite:///:memory:`를 설정했다. 장면 생성 호출은 로컬 mock으로 대체했다. [재현 코드](writing-repro.py)와 [원본 출력](writing-repro-output.txt)을 함께 보관했다. `backend`에서 `.venv/Scripts/python.exe -B -c "exec(open('../docs/audits/writing-repro.py', encoding='utf-8').read())"`로 다시 실행할 수 있다. 실행 종료 코드는 0이다.
- **확정 버그**는 코드 경로와 재현으로 확인한 계약 위반이다. **설계 한계**는 구현이 제공하지 않는 보장이다. 실제 생성 문학성·독자 반응은 이번 감사로 평가하지 않았다.

## 요약

현재 제품은 **작가가 설정을 고르고 초고를 검토하는 회차 집필 보조 도구**로는 기반이 좋다. 그러나 **100화 이상의 상태·인과를 지속해서 관리하는 엔진**이라고 보기는 어렵다. 회차 수보다 중요한 것은 회차별 사실의 유효 시점, 이전 선택의 대가, 관계 변화, 독자가 아는 정보다. 이 정보가 정본으로 누적되거나 집필·감수에 일관되게 전달되지 않는다.

우선순위는 모델 증설이나 병렬 수 확대보다 **정본 컨텍스트 → 생성 → 독립 검증**의 연결을 바로잡는 것이다.

## 잘된 점

1. **사건보다 선택·대가를 앞세운 계약**: 회차 브리프에 감정 목표·핵심 사건·인물 선택·대가·금지·다음 훅을 요구한다. 장면 계획에도 objective/choice/cost와 required_beats가 있다. 산문 생성만 요청하는 것보다 작가 의도를 명시하기 좋다. (`backend/app/schemas.py:298-313`, `:361-385`)
2. **계층별 집필 재료**: 부트스트랩 목차를 회차 메모로 저장하고 권 개요·감정 곡선·고봉을 별도 보관한다. 생성 시 현재 목차·권 방향·직전 화 말미·다음 화 방향을 함께 넣을 수 있다. (`backend/app/services/bootstrap.py:560-570`, `backend/app/routers/ai_panel.py:202-243`)
3. **원고를 임의 확정하지 않는 검토 흐름**: canon은 문제 후보를 반환하고 이력을 저장한다. 병렬 감수는 수정본을 만들지 않는다. 자동 주입 목록도 SSE 시작 이벤트로 공개한다. (`backend/app/routers/quality.py:28-67`, `backend/app/routers/ai_panel.py:81-89`, `:539-544`)
4. **기본 실행 안정성**: 병렬 worker 수 제한, 실패 시 나머지 취소, 장면 순서·누락 검사, 메타 마커 유출 차단이 있다. 부트스트랩은 마지막 한 번의 commit으로 구조를 저장한다. 이는 문학성 보장은 아니지만 필요한 기반이다. (`backend/app/services/parallel_writer.py:49-88`, `:112-155`, `backend/app/services/bootstrap.py:523-529`, `:627`)

### W2 · P1 — 최우선 브리프의 고유명사가 자동 로어 검색에는 전달되지 않는다

**확정 누락 + 검색 설계 한계.**

- 브리프는 프롬프트 `blocks`에만 들어간다. 로어 검색 `source_parts`는 장면/회차 본문, 조건부 회차 메모, `prompt_override`로 만든다. 브리프와 preset 본문은 검색어에 없다. (`backend/app/routers/ai_panel.py:178-201`, `:259-268`, `:304-307`)
- **재현**: 빈 회차에서 `auto_lore=True`, 브리프 사건에만 "은빛목걸이를 찾아낸다"를 넣었다. 동일 제목·키워드를 가진 로어가 DB에 있어도 `injected_lore=[]`였다. 브리프는 모델에 전달되지만 유물의 실제 규칙은 빠진다.
- 관련 추가 한계: 생성은 선택한 캐릭터 필드만 읽고 `Relationship`을 읽지 않는다. Project의 장르·시놉시스·주제 메타도 자동 주입하지 않는다. 재현의 `SYNOPSIS_SENTINEL`은 메시지에 없었다. (`backend/app/routers/ai_panel.py:244-258`, `:293-330`)
- `semantic`은 의미 임베딩이 아니라 문자 2-gram 코사인이다. 항목을 매 요청 전부 읽고 각 항목에 대해 query 벡터를 다시 만든다. 별칭·동의어·지시대상의 의미 이해를 보장하지 않는다. (`backend/app/services/semantic.py:18-51`, `backend/app/services/injection.py:72-88`)
- **우선 수정**: 최종 지시·브리프·목차에서 검색 질의를 한 번 생성한다. 선택된 인물의 관계와 작품 핵심 전제를 동일 context builder에서 제공한다. 대규모 로어에는 사전 계산한 검색 인덱스와 토큰 예산을 둔다. UI에는 현재 검색을 "문자 유사도 보강"으로 설명한다.
- **회귀 기준**: 브리프에만 등장한 설정도 검색된다. 동일한 계약을 순차/병렬 생성과 canon에 전달하며, 어떤 근거를 생략했는지 확인할 수 있어야 한다.

### W3 · P1 — 작품 문체 프로파일이 병렬 생성과 일반 수정 감수에서 사라진다

**확정 버그.**

- `_build_messages`는 프로젝트 문체를 **system 메시지**에 붙인다. 병렬 경로는 그 결과 중 user 메시지만 가져가고, worker system을 다시 `NOVEL_SYSTEM_PROMPT`로 만든다. planner와 reviewer에도 문체가 전달되지 않는다. (`backend/app/routers/ai_panel.py:314-329`, `:650-652`, `:703-715`, `:778-785`)
- 일반 감수도 생성의 user 메시지만 복사하므로 작품 문체가 빠진 상태에서 전체 수정본을 쓴다. (`backend/app/routers/ai_panel.py:577-581`)
- **재현**: `style_profile=True`와 `STYLE_SENTINEL` 설정 시 일반 생성 메시지에는 해당 값이 있었다. 병렬 planner/worker 2개/reviewer의 실제 함수 호출 메시지에는 모두 없었다: `[False, False, False, False]`.
- **영향**: 사용자가 켠 문체 유지 기능이 생성 모드에 따라 무효가 된다. 일반 초안의 문체도 감수 수정본에서 바뀔 수 있다. 실제 문체 변화량은 별도 평가가 필요하지만 전달 누락은 확정이다.
- **우선 수정**: 역할 지시와 작품 불변 계약을 분리한다. 문체·시점·서술 인칭 같은 계약은 모든 작성/수정 역할에 공통 전달한다. 프롬프트 캡처 테스트로 각 단계의 동일 계약을 검증한다.

### W4 · P1 — 부족한 AI 목차를 채울 때 권 배치와 정렬 순서가 중복된다

**확정 버그.**

- `_coerce_outline`은 권별 부족분이 아니라 전체 결과 개수로 부족분의 권·화·정렬값을 계산한다. 입력 권 번호와 화 번호의 중복·요청 범위 초과도 엄격히 검증하지 않는다. (`backend/app/services/bootstrap.py:263-292`)
- **재현**: 요청은 2권×2화. 응답은 1권에 A 1개, 2권에 B/C 2개였다. 보정 결과는 아래와 같다.

```text
(volume, order, sort_order, title)
(1, 1, 0.0, A)
(2, 1, 2.0, B)
(2, 2, 3.0, C)
(2, 2, 3.0, 2권 2화)
```

- **영향**: 1권 부족분은 남고 2권 2화가 중복된다. 같은 sort_order끼리는 직전/다음 회차 조회의 엄격한 `<`, `>` 비교에서 서로 보이지 않는다. (`backend/app/routers/ai_panel.py:219-234`)
- AI 결과 부족 시 고정 판타지 캐릭터·빈 내용 로어도 자동 보충한다. 결과 표시는 실제 보충 여부가 아니라 `generated_by` 값만으로 `used_ai`/`fallback`을 정한다. 장르에 맞지 않는 템플릿 혼합을 별도로 알리지 않는다. (`backend/app/services/bootstrap.py:367-373`, `:399-440`, `:643-644`)
- **우선 수정**: 권별 예상 슬롯을 검증하고 정렬값을 최종 배열에서 한 번 부여한다. 부족/중복/범위 초과는 부분 재생성 또는 사용자 승인 대상으로 반환한다. 템플릿 보충 여부와 누락 필드를 명시하고, "AI가 완성한 설정"과 구분한다.

### W5 · P1 — 100화 이상 부트스트랩도 목차 생성은 한 번이며 후속 설정에는 앞부분만 남는다

**설계 한계. 대량 요청 실패를 실측한 것은 아니다.**

- API는 최대 50권×200화를 허용하지만 전체 회차의 2문단 시놉시스와 핵심 사건을 한 응답에 요청한다. 권별 분할 생성·체크포인트·재개가 없다. (`backend/app/schemas.py:642-647`, `backend/app/services/bootstrap.py:124-150`, `:681-688`)
- 후속 인물/로어 생성용 목차 앵커는 12,000자에 닿으면 즉시 반환한다. 앞에서부터 채우므로 후반 권의 설정은 사라진다. 인물/관계 지침도 여전히 "1권" 중심이다. (`backend/app/services/bootstrap.py:29-33`, `:155-175`, `:199-212`, `:315-344`, `:690-701`)
- 반대편에서는 canon이 모든 인물·로어·설치/보류 복선을 길이 제한 없이 한 번에 넣는다. 저장량이 늘어도 입력 토큰 예산이나 중요도별 축약이 없다. (`backend/app/services/canon.py:46-79`)
- **영향**: 장편은 한 번에 설계하기에는 응답이 크고, 후속 설정에는 뒤쪽 사건이 빠지며, 장기 감수 입력은 다시 무제한으로 커진다. 구조 저장 개수가 많다는 것과 장편 서사 지원은 다르다.
- **우선 수정**: 작품 전체 아크 → 권 아크 → 근접 회차 브리프 순으로 계층 계획을 만든다. 아직 쓰지 않은 먼 회차는 저해상도 계획으로 유지한다. 완료한 권/회차만 부분 재생성할 수 있도록 버전·승인·체크포인트를 둔다.

### W6 · P2 — 병렬 조립은 형식 검증이지 장면 연결의 품질 게이트가 아니다

**설계 한계.**

- worker는 공통 회차 지시와 자기 계약만 받는다. 다른 worker가 실제로 쓴 결말은 볼 수 없다. 결과 검사는 빈 문자열·최대 12,000자·메타 마커·순서·제목만 확인한다. (`backend/app/routers/ai_panel.py:701-729`, `backend/app/services/parallel_writer.py:49-88`)
- **재현**: objective/choice/cost/required_beats를 갖춘 정상 계획에 대해 각 장면을 한 글자 `가`로 반환해도 `validate_results=[]`다.
- 조립 원고는 감수 전에 `message`로 전송되고, 감수는 의견만 반환한다. 구조화된 통과/불통과나 승인 대기 상태가 없다. (`backend/app/routers/ai_panel.py:742-753`, `:778-812`)
- **영향**: 앞 장면에서 문을 부쉈는데 다음 장면에서 열쇠를 찾는 등의 접합부 모순은 계약만으로 막을 수 없다. 회차 목표 분량도 각 worker에 같은 전체 브리프로 전달되므로 장면별 배분이 없다.
- **우선 수정**: 인과적으로 의존하는 장면은 순차 집필하고 독립 장면만 병렬화한다. 병렬 결과에는 실제 종료 상태를 추출하고 다음 시작 상태와 비교하는 접합부 검사·국소 수정 단계를 둔다. "초안 조립 완료"와 "감수 승인"을 분리한다.

### W7 · P1 — 잘못된 canon JSON을 "모순 없음"으로 받아들일 수 있다

**확정 버그.**

- `parse_issues`는 `issues`가 없으면 빈 목록을 기본값으로 사용한다. 배열 요소가 dict가 아니거나 quote/reason이 없으면 조용히 버린다. JSON 형식만 맞으면 응답 스키마 위반이 repair 대상이 되지 않는다. (`backend/app/services/canon.py:95-110`, `:125-135`)
- **재현**: `{}`와 `{"issues":"not-an-array"}`는 모두 `[]`로 반환됐다. `{"issues":null}`은 `TypeError`다. 이 예외는 service 재시도와 router의 ValueError 처리에서 잡히지 않는다. (`backend/app/routers/quality.py:43-54`)
- 인용문이 실제 본문에 있는지도 검증하지 않는다. 검사 이력에는 model/문제/컨텍스트 개수만 저장되고, 대상 본문 해시나 설정 버전은 없다. (`backend/app/services/canon.py:101-109`, `backend/app/models.py:144-153`)
- **영향**: 검사 형식 실패와 "설정 모순 0건"이 구분되지 않는다. 본문 수정 후 과거 검사 결과가 어느 원고에 해당하는지도 엄밀히 추적하기 어렵다.
- **우선 수정**: 필수 `issues` 배열과 항목을 스키마로 엄격히 검증한다. 파싱 실패는 재시도 후 "검사 실패"로 반환한다. quote의 본문 일치 여부, 본문 해시·정본 스냅샷 버전·검사기 버전을 저장한다.

### W8 · P2 — 품질 점수·감수 의견·프로토콜 통과는 독립적인 소설 품질 증거가 아니다

**점수 구현 문제 + 평가 설계 한계.**

- **재현**: 빈 원고가 65점이다. `"가나다라?" 마바사아자차카타파하.`는 공백/기호 제외 14자로 100점이다. 분량 부족은 제안만 추가하고 감점하지 않는다. 훅은 마지막 300자의 물음표·느낌표 등 문자열 존재로 판정한다. (`backend/app/services/quality.py:35-43`, `:71-74`, `:78-135`)
- 문단 5개 이상에서만 길이/첫머리 감점을 적용하므로 짧은 입력은 일부 규칙을 우회한다. `WEAK_ENDINGS`의 `~`도 실제 검색 문자열에 포함되어 "일 뿐이다" 같은 자연문장을 해당 약한 어미로 세지 못한다. (`backend/app/services/quality.py:28`, `:58-59`, `:95-119`)
- 시스템 프롬프트는 장면 유형에 맞추고 보편 대사 비율을 정하지 말라고 하지만 점수는 장면 유형 입력 없이 "35~50%가 연재 관례"라는 고정 제안을 낸다. 그 비율이 실제 독자 선호를 예측한다는 근거는 이 엔진에 없다. (`backend/app/routers/ai_panel.py:38-46`, `backend/app/services/quality.py:84-99`)
- 평가 스크립트는 offline에서 코퍼스 스키마만 확인하면서 `protocol_pass=len(cases)`를 출력한다. schema-only라는 주의문은 존재한다. live의 `ok`도 SSE 순서·비어 있지 않음으로 결정하고 required/forbidden cue 위반은 별도 집계만 한다. (`backend/scripts/evaluate_parallel.py:40-55`, `:112-117`, `:123-134`)
- **Mandela 감사**: 생성과 감수가 같은 엔드포인트/기본 모델을 쓸 수 있어 **Shared hallucination** 위험이 있다. 자체 프롬프트의 표면 지침과 자체 규칙 점수를 품질 근거로 해석하면 **Tautology**가 된다. 이는 실제로 잘못된 소설이 생성됐다는 증거가 아니라, 현재 지표만으로 좋은 소설이라고 결론낼 수 없다는 뜻이다. (`backend/app/routers/ai_panel.py:520-532`, `backend/app/routers/quality.py:35-47`)
- **우선 수정**: 100점 대신 "문장 형식 진단"으로 명명하고 빈/극단적 단문은 평가 불가로 표시한다. 프로토콜 테스트·계약 준수·연속성·독자 평가를 분리한다. 작가가 별도로 확정한 사실 원장과 독립 편집자가 만든 오류/정상 장편 사례로 precision/recall을 확인한다. 문학성은 모델·생성방식을 가린 비교 평가와 실제 독자 반응으로 별도 확인한다. 모델만 바꾸는 것은 독립 근거의 대체가 아니다.

## 권장 실행 순서

1. **즉시 신뢰성 수정**: W3 문체 전달, W4 목차 보정, W7 canon 응답 검증. 각각 작은 mock/정규화 회귀 테스트로 확인할 수 있다.
2. **집필 품질의 최우선 구조 개선**: W1 시점별 정본 원장과 W2 공통 context builder. 원고에서 발생한 변화는 작가 승인 후 정본으로 확정한다.
3. **장편 확장**: W5 계층 계획과 재개 가능한 권/회차 생성. 토큰 예산·검색 근거·누락 정보를 함께 제공한다.
4. **그 후 병렬·품질 최적화**: W6 인과 의존 장면 분리와 W8 독립 평가. 속도 개선이 일관성을 해치지 않는지 비교한다.
