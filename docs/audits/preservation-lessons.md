# 원고 보존 구현에서 남길 검증 규칙

범위: 원고 보존 1단계. 아래는 문학적 품질의 평가가 아니라 데이터 손실을 막기 위한 후속 개발 규칙이다.

## 1. 비동기 작업은 응답 수신이 아니라 소유권·입력 순서로 완료한다
- 재사용할 계약: `(project_id, chapter_id)`와 작업 시작 시 입력 순서를 캡처한다. 응답은 해당 회차·보낸 입력까지만 확인한다.
- 금지 패턴: 오래된 저장/교체 응답으로 현재 편집 내용을 무조건 초기화하거나 브라우저 복구본을 삭제하기.
- 다음 변경의 필수 시험: 저장과 모든 본문 교체 요청을 각각 보류하고 새 입력·회차 전환 후 응답을 풀어 본문, revision, 브라우저 저장소를 확인한다.
- 근거: `preservation-task-2-review.md`, `preservation-task-2-rereview-1.md`.

## 2. 복구 선택은 하나의 상태 전이로 검증한다
- 재사용할 계약: 미해결 복구에서는 편집을 명확하게 잠그거나, 허용한 모든 입력을 기존 복구본과 함께 보존해야 한다. 본문과 기준 버전은 같은 조회의 쌍이어야 한다.
- 금지 패턴: flush 한 곳만 막기, 오류를 삼킨 뒤 성공 처리를 계속하기, 서버 조회 실패 후 로컬 복구본 삭제하기.
- 다음 변경의 필수 시험: 복구 진입→입력 가능 여부→캐시 갱신→조회 실패→재시도→중복 선택→명시적 선택→저장 대기→재로딩을 연결해서 확인한다. 성공뿐 아니라 실패/지연 때의 저장소와 잠금 상태도 검사한다.
- 근거: `preservation-final-spec-review.md`, `preservation-final-spec-rereview-1.md`, `preservation-final-spec-rereview-2.md`, `preservation-final-spec-rereview-3.md`.

## 3. 보존 증거는 실제 경계에서 얻는다
- 재사용할 계약: 본문·revision·교체 전 snapshot은 한 트랜잭션이며, 충돌 버전은 세션 캐시가 아닌 실제 DB 값이다.
- 금지 패턴: 캐시된 revision 반환, 예외 모의 주입만으로 DB rollback을 증명하기, 빈 DB 업그레이드만으로 참조 데이터 보존을 주장하기, 모의 API 시험을 실제 통합으로 부르기.
- 다음 변경의 필수 시험: 두 실제 DB 세션의 경합, 실제 unique 오류 rollback, 참조 행이 있는 과거 스키마 업그레이드, SQLite 백업의 전체 행 비교, 실제 임시 서버 응답을 쓰는 브라우저 시험을 유지한다.
- 근거: `preservation-task-1-review.md`, `preservation-task-1-rereview-1.md`, `preservation-final-validation.md`.

## 후속 범위
안전한 저장 모듈·필수 revision 계약·격리 시험 환경은 유지한다. 이번에 승인하지 않은 서사 기억·기획·완결 기능은 별도 설계와 승인 후 진행한다. 테스트 개수 증가만으로 소설 품질이나 운영 데이터 복원까지 검증했다고 주장하지 않는다.
