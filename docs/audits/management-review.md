# 원고·장편 관리 백엔드 감사

## 범위와 검증

현재 작업 트리의 프로젝트·회차·장면·캐릭터·로어·복선·권 개요, 원고 보존, DB 마이그레이션을 검토했다. 역사적 HANDOFF나 과거 QA의 PASS를 현재 동작의 증거로 쓰지 않았다.

- 구현과 실제 DB는 변경하지 않았다. 보고서와 요청받은 재현 코드·출력만 `docs/audits`에 작성했다.
- 실제 프로젝트 환경인 `backend/.venv/Scripts/python.exe`에서 FastAPI `TestClient`와 SQLite 메모리 DB를 사용했다. `DATABASE_URL=sqlite://`, `StaticPool`, 프로젝트의 FK 프라그마를 적용했다. 실행 중 서비스에는 접속하지 않았다.
- 외부·유료 LLM을 호출하지 않았다. 전체 테스트 스위트는 상위 감사 담당 범위다.
- 재현 코드와 원시 출력: [API 재현](management-api-repro.py), [API 출력](management-api-output.txt), [마이그레이션 재현](management-migration-repro.py), [마이그레이션 출력](management-migration-output.txt). `backend`를 cwd로 두고 native Python의 `-c`에서 해당 파일을 UTF-8로 읽어 `exec`하면 재실행할 수 있다.
- API 재현은 실제 라우터·ORM·응답 직렬화를 거쳤다. 윤문 수락 검증만 외부 파이프라인 대신 `RefineRun` fixture를 직접 넣었다. 따라서 윤문 생성 품질이나 파이프라인 성공 여부는 검증하지 않았다.

## 잘 된 점

1. **장편 관리의 기본 단위가 갖춰져 있다.** 프로젝트→회차→장면 계층, 권별 개요·감정 곡선·고봉 노트, 인물 카드·관계, 로어 키워드, 복선 설치·회수 상태를 분리했다. `backend/app/models.py:21-141`, `backend/app/models.py:190-233`.
2. **기본 무결성과 저장 방식은 좋은 출발점이다.** SQLite WAL·쓰기 대기·FK 검사를 공통 적용한다. 본문 저장과 글자 수 캐시는 같은 트랜잭션에서 갱신한다. `backend/app/database.py:16-39`, `backend/app/routers/projects.py:205-213`.
3. **일부 경계 검사는 정확하다.** 회차 일괄 정렬은 중복·타 작품 ID를 변경 전에 거부한다. 인물 관계 생성도 양쪽의 작품 소속을 검사한다. `backend/app/routers/projects.py:235-258`, `backend/app/routers/characters.py:108-119`.
4. **작가의 명시적 선택을 존중한다.** 장면 조립은 명시 호출이고, 윤문은 수락 시만 반영한다. 윤문 원문·결과와 canon·품질 진단 이력을 보관한다. 다만 일반 원고 버전 기록은 아니다. `backend/app/routers/scenes.py:99-117`, `backend/app/routers/refine.py:58-75`, `backend/app/models.py:144-169`.

## 우선 발견 사항 8개

### M1 · P0 · 확정 버그: 오래된 윤문 수락이 최신 수동 원고를 덮어쓴다

- **증거:** `backend/app/routers/refine.py:96-115`는 실행의 처리 상태만 검사하고 현재 본문과 윤문 당시 원문을 비교하지 않는다. 원문은 이미 `report_json.original_text`에 저장한다(`:62-69`). 일반 저장 스키마도 `content_md`만 받는다(`backend/app/schemas.py:57-60`).
- **재현:** 원문 A로 만든 실행을 준비 → 원고를 B로 수동 저장 → 이전 실행 accept. HTTP 200이며 B가 이전 윤문 결과로 교체됐다.
- **영향:** 긴 회차를 다듬는 동안 생긴 최신 수정이 사라진다. 일반 본문 PUT 역시 버전 검사가 없으므로 오래된 탭·지연 요청을 구분하지 못한다. 후자는 코드로 확인한 설계 한계이며 실제 동시 요청 경쟁을 별도로 측정하지 않았다.
- **수정:** 회차 revision 또는 content hash를 저장 요청·윤문 실행에 넣고 불일치는 409로 막는다. 사용자에게 비교·재실행을 제공한다. 교체 직전 본문 스냅샷을 남겨 복원할 수 있게 한다.

### M2 · P0 · 확정 버그: 원고와 윤문 이력이 있는 구버전 DB의 업그레이드가 실패한다

- **증거:** `backend/alembic/versions/b3c4d5e6f7a8_chapter_volume_nullable.py:22-24`의 batch 변경은 chapters를 재생성한다. 마이그레이션 엔진은 FK ON을 그대로 적용한다(`backend/alembic/env.py:42-53`, `backend/app/database.py:29`).
- **재현:** 실제 Alembic으로 `a1b2c3d4e5f6`까지 생성 → 프로젝트·회차·해당 회차를 참조하는 `refine_runs` 1건 생성 → `upgrade head`. `DROP TABLE chapters`에서 `IntegrityError: FOREIGN KEY constraint failed`로 실패했다. 연결만 메모리 DB에 고정했고 실제 마이그레이션 함수를 실행했다.
- **영향:** 빈 DB에서는 통과해도 사용하던 작품 DB의 업그레이드가 막힌다. 실제 운영 DB가 현재 구버전인지 또는 이미 손상됐는지는 조사하지 않았다.
- **수정:** 백업을 전제로 SQLite batch 재생성의 FK 처리·트랜잭션 절차를 명시하고, 완료 뒤 `foreign_key_check`와 본문·관계 보존을 검사한다. 모든 주요 과거 revision에 실제 데이터가 있는 업그레이드 테스트를 추가한다.
- **별도 설계 한계:** 앱 시작은 `create_all`만 호출한다(`backend/app/main.py:16-25`, `backend/app/database.py:54-58`). 기존 테이블의 컬럼 업그레이드를 수행하지 않는다. 시작 전 schema revision 검사와 명시적 마이그레이션 안내가 필요하다. 현재 `backend/tests/test_migrations.py:33-62`는 빈 DB의 테이블 생성·롤백 위주라 이번 사례를 담지 않는다.

### M3 · P1 · 확정 버그: 다른 작품의 장면 순서를 변경할 수 있다

- **증거:** `backend/app/routers/scenes.py:75-92`는 요청한 회차의 존재만 확인한다. 장면 조회 조건은 `Scene.id.in_(ids)`뿐이고 `Scene.chapter_id == cid`가 없다.
- **재현:** 작품 A 회차의 `/scenes/order`에 작품 B 장면 ID를 보내면 HTTP 200이고 B 장면의 `sort_order`가 1→99로 바뀐다. 응답에는 A의 장면만 나오므로 잘못된 변경도 드러나지 않는다.
- **영향:** 여러 작품을 오가거나 UI 상태가 오래됐을 때 다른 작품의 장면 순서가 훼손될 수 있다. 멀티유저 권한 취약점이라고 확장해 주장하지 않는다.
- **수정:** 회차 소속을 조회 조건에 포함한다. 존재·소속·중복 검사를 완료한 뒤만 변경한다. 타 회차·타 작품 ID가 하나라도 섞이면 422와 전 항목 불변을 검사한다.

### M4 · P1 · 확정 버그: 복선의 작품 경계와 참조 객체 삭제 규칙이 빠져 있다

- **증거:** 복선 참조 검사는 회차의 존재만 확인한다(`backend/app/routers/foreshadows.py:201-205`, `:224-246`). 복선의 회차 FK에 `ON DELETE SET NULL`이 없다(`backend/app/models.py:116-119`). 캐릭터 삭제도 관계 정리 없이 commit한다(`backend/app/routers/characters.py:95-99`, `backend/app/models.py:207-220`).
- **재현:** A 작품 복선의 설치 회차로 B 작품 회차를 지정해 생성 성공. 그 B 회차 삭제는 HTTP 500. 관계로 연결된 캐릭터 삭제도 HTTP 500.
- **영향:** 복선의 출처가 다른 작품으로 섞이고 정상적인 구조 정리가 막힌다. FK가 삭제를 거부하므로 이번 재현에서 데이터가 삭제되거나 고아 행이 생긴 것은 아니다. 원치 않는 삭제를 막을 의도라도 500 대신 안내가 필요하다.
- **수정:** 설치·회수 회차를 복선과 같은 작품으로 제한한다. 회차 삭제 시 복선 참조를 해제할지, 409로 막고 연결을 표시할지 정한다. 인물 삭제는 관계를 양방향 정리하거나 관계 목록과 함께 409를 반환한다. 관계가 있는 작품 전체 삭제와 회차 삭제도 함께 회귀 검증한다.

### M5 · P1 · 확정 버그: 빈 작품의 복선 알림이 500이고 권별 시간축도 다르다

- **증거:** `backend/app/routers/foreshadows.py:48-54`는 복선이 없을 때만 조기 반환하고, 회차가 없어도 `chapters[-1]`을 읽는다. 정렬 기준도 `Chapter.sort_order`뿐이다. 회차 목록은 권→순서 정렬이다(`backend/app/routers/projects.py:164-168`).
- **재현:** 회차 없이 복선만 하나 만든 뒤 `/foreshadows/reminder` 조회 → HTTP 500.
- **장편 영향:** 집필 전에 복선을 기획하는 기본 흐름이 깨진다. 권별 sort_order를 재사용하면 최신 회차·경과 회차 계산이 서사 순서와 달라질 수 있다. 후자는 코드로 확인한 순서 불일치이며 대규모 작품에서 별도 부하·UI 검증은 하지 않았다.
- **수정:** 빈 회차를 정상 응답으로 처리한다. 권·회차·동순위 ID를 포함한 공통 서사 순서를 목록, 이전 회차, 리마인더에서 공유한다. 미집필 예정 회차를 경과 시간에 포함할지도 명시한다.

### M6 · P1 · 확정 버그: 다른 작품의 로어가 검색 결과 한도를 먼저 차지한다

- **증거:** `backend/app/services/fts.py:102-117`는 전역 FTS에서 먼저 LIMIT을 건다. 작품·카테고리 필터는 이후 적용한다(`backend/app/routers/lorebook.py:71-79`, `:95-97`).
- **재현:** A와 B에 동일한 `dragon` 로어를 각각 생성. B 작품에서 `q=dragon&limit=1` 검색 시 HTTP 200이지만 `[]`. B 로어는 존재한다.
- **영향:** 설정이 많아질수록 실제로 있는 설정을 못 찾는다. 기본 limit=100에서도 다른 작품의 상위 매치가 한도를 채우면 같은 구조로 누락된다. 타 작품 데이터가 응답으로 노출된 것은 아니다.
- **수정:** FTS와 원본 테이블을 조인하고 project_id·category를 적용한 뒤 정렬·LIMIT한다. 다작품·다카테고리에서 낮은 limit으로 재현하는 테스트를 유지한다.

### M7 · P2 · 확정 버그: 일괄 정렬에서 회차의 권 배정을 해제할 수 없다

- **증거:** reorder 스키마는 `volume: int | None`을 받지만(`backend/app/schemas.py:222-229`), 구현은 `item.volume is not None`일 때만 변경한다(`backend/app/routers/projects.py:251-256`).
- **재현:** 1권 회차에 `items:[{id:...,volume:null}]` → HTTP 200이나 volume은 여전히 1이다. 단건 PATCH와 일괄 이동의 의미가 다르다.
- **영향:** 권 구조를 재편하고 평면 회차로 옮기는 작업이 성공처럼 보이면서 반영되지 않는다.
- **수정:** 필드 생략과 명시적 null을 구분한다. 예를 들어 `model_fields_set`으로 제공 여부를 확인한다. 유한한 정렬값과 동순위 정책도 함께 정의한다.

### M8 · P1 · 설계 한계: 일반 원고 복구가 DB 수동 복사에 의존한다

- **증거:** `backend/app/routers/system.py:1-5`는 백업·복원 API를 만들지 않고 파일 위치만 안내하는 의도된 설계를 명시한다. 회차·장면 본문은 현재값 하나이며 일반 수정 이력이 없다(`backend/app/models.py:49-94`). 본문 PUT과 장면 조립은 현재값을 교체한다(`backend/app/routers/projects.py:205-211`, `backend/app/routers/scenes.py:113-117`). 삭제도 물리 삭제다(`backend/app/routers/projects.py:227-231`).
- **판정:** 백업 기능이 있다고 주장하거나 현재 백업이 손상됐다고 주장하지 않는다. 수동 백업 자체는 의도된 MVP 범위다. 다만 장편 집필의 핵심 자료에 비해 실수 복구 단위가 너무 크다.
- **검증 사각지대:** `scripts/backup_verify.py:13-27`은 서비스가 응답하는 상태에서 DB·WAL·SHM을 각각 복사한 뒤 일부 테이블의 행 수만 비교한다. 본문 동일성, 장면·복선·관계·진단 이력, 복원 후 구동은 검증하지 않는다. 이 스크립트는 실행하지 않았다.
- **수정:** 우선 본문 revision·변경 전 스냅샷·회차 휴지통을 추가한다. 다음으로 일관된 SQLite 백업 API 또는 서버 정지 기반 백업 절차, 백업 무결성 검사, 별도 DB로 복원해 여는 검증을 제공한다. 작품별 Markdown/JSON 내보내기도 장기 보관과 도구 이동을 위한 별도 가치가 있다.

## 권장 실행 순서

1. **원고를 잃지 않게 한다:** M1 충돌 차단·교체 전 보존, M2 기존 데이터 마이그레이션, M8 검증 가능한 복구 경로.
2. **장편의 구조와 설정을 믿을 수 있게 한다:** M3·M4 작품 경계와 참조 정리, M5 통일된 회차 시간축, M6 프로젝트 내부 검색.
3. **재구성 작업을 다듬는다:** M7 권 배정 해제. 이후 모든 목록을 한 번에 읽는 현재 구조의 페이지네이션·필터·대용량 응답을 실제 작품 규모로 측정한다. 이번 감사에서는 대규모 성능을 측정하지 않았으므로 성능 버그라고 단정하지 않는다.

## 검증 해석과 남은 일

확정 버그는 실제 API 응답·DB 읽기 또는 Alembic 오류로 확인했다. 메모리 DB의 단일 프로세스 검증이므로 운영 파일 시스템, 전원 장애, 브라우저 자동저장, 실제 사용자 백업 복원은 검증하지 않았다. 별도 fresh reviewer는 하위 에이전트 생성 금지에 따라 실행하지 않았으며 상위 감사에서 검토해야 한다. 이 보고서는 수정 승인이나 전체 제품 QA 통과 선언이 아니다.
