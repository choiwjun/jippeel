## 결론

**집필 보조 도구의 구성은 좋지만, 현재 기능 수가 실제 집필 신뢰성을 앞서 있다.** 우선순위는 기능 추가보다 **원고 보존 → AI 맥락 연결 → 장편 설정의 시간축 → 독립적인 품질 검증**이다.

현재 코드를 기준으로 진단했다. 구현 변경이나 운영 원고 변경은 하지 않았다. 새 유료·실모델 생성은 실행하지 않았으므로 문학적 재미나 상용 연재 수준을 확정하지 않는다.

## 2. 잘된 점

1. **소설 작업의 기본 단위가 갖춰져 있다.** 작품·권 기획·회차·장면·캐릭터·관계·세계관·복선을 분리해 관리한다. 단순 채팅보다 구조적으로 확장하기 좋다.
2. **작가가 최종 반영을 결정한다.** 생성 초안·감수 의견·수정본을 분리하고 명시적 반영을 요구한다. 감수 실패 때 초안을 보존하는 경로도 있다. 다만 반영 대상과 버전 보호는 보강해야 한다.
3. **회차를 설계하는 입력이 있다.** 브리프에 감정 목표·사건·인물 선택·대가·금지사항·다음 화 훅을 표현하고, 장면 계약과 병렬 작업에 전달한다. 프롬프트 한 줄보다 집필 의도를 명확히 할 기반이다.
4. **장편 일관성을 지원할 재료가 있다.** 목차·권 개요·이전 회차·문체 프로파일·설정 자동 주입·모순 검사·복선 리마인드가 구현돼 있다. 그러나 UI 연결·시간축·검색 한계 때문에 존재 자체를 실효성으로 볼 수는 없다.
5. **테스트와 안전 장치의 기반이 있다.** 임시 DB API 테스트, FK 검사, 원자적 reorder 일부 경로, JSON 재시도, SSE 이벤트 테스트, 브라우저 테스트가 있다. 미리보기 정화와 키 마스킹도 유지할 장점이다.

## 4. 소설 작성 능력의 핵심 한계

### A. 품질 점수는 소설 완성도 점수가 아니다

직접 함수 실행 결과 **빈 원고 65점**, **`"가나다라" 마바사!` 100점**이다. 느낌표만으로 후크가 있다고 판단한다. 분량 미달은 제안에만 반영된다. 약한 어미 검색은 `~`를 문자 그대로 찾는 오류도 있다.

따라서 지금은 **문체 규칙 점검**으로 이름을 바꾸고 종합 점수를 강한 품질 주장에 쓰지 않는 것이 맞다. 재미·인과관계·감정 변화·인물 고유성·떡밥 회수·설정 일관성을 별도 평가해야 한다. `metrics_v2`의 essay 장르 고정도 소설 전용 기준인지 검증이 필요하다.

### B. 장편 기억은 단순 검색·짧은 발췌를 넘어서야 한다

현재 선택·절단 방식은 모든 과거 사건을 추적하는 기억 체계가 아니다. `semantic.py`도 문자 2-gram 유사도라 의미 임베딩이나 대명사 해소와 같지 않다. 회차 브리프에만 등장하는 설정이 자동 로어 검색에서 빠지는 재현도 있다.

권장 구조:
- **확정 설정**: 인물 정체·능력·세계 규칙 + 근거 원고 위치.
- **회차별 상태**: 시각·장소·부상·소지품·인물 관계·알고 있는 사실.
- **독자 공개 상태**: 작가만 아는 사실, 독자만 아는 사실, 인물별 인지 분리.
- **회차 요약·사건 변화분**: 원고 승인 때 추출 후보를 만들고 작가 확인 후 확정.
- 검색 결과에는 근거·적용 시점·누락 이유·입력 예산을 표시한다. 임베딩 교체만으로 해결됐다고 보지 않는다.

### C. 병렬 집필은 속도 기능이지 품질 보장이 아니다

장면 계약은 좋지만 각 작업자는 앞 작업자의 실제 완성 장면을 보고 이어 쓰는 방식이 아니다. 한 글자 장면도 현재 결정적 검사를 통과한다. 목표 분량과 사건 이행 여부가 강한 완료 조건이 아니다.

권장: 서로 독립적인 장면만 병렬화하고, 인과관계가 강한 장면은 순차 생성한다. 최종 통합 단계에서 시간·소품·감정·반복 도입·문체를 점검하고, 수정본과 초안을 비교해 작가가 채택하게 한다. 단일 집필보다 실제로 나은지는 블라인드 비교로 확인한다.

### D. 감수는 의견이며 독립적인 정답이 아니다

동일 계열 모델의 생성·감수 반복만으로 품질을 입증할 수 없다. 모순 검사도 전체 장편을 모두 읽는 것이 아니라 제한된 맥락을 본다. ‘통과’보다 **검사한 범위/검사 못한 범위/근거 구절/불확실성**을 보여줘야 한다.

## 5. 관리 능력 고도화

- **원고 버전 관리**: 자동저장 이력, 생성·윤문 반영 직전 스냅샷, diff, 되돌리기, 삭제 휴지통.
- **장면과 회차의 관계 명확화**: 장면 원고와 회차 원고가 따로 변한다. 조립 시 미리보기·버전 확인·덮어쓰기 경고·되돌리기 제공.
- **검증 가능한 백업·복원**: DB의 일관된 스냅샷, 실제 복원 시험, 원고 외 설정·복선·장면·기획 보존 확인. 현재 수동 복사 검증은 일부 테이블 행 수 비교여서 완전 복구 증거가 아니다. AI 키 복호화 가능성도 별도 확인해야 한다.
- **장편 관리 화면**: 타임라인, 인물 상태 변화, 복선 설치·회수 예정일, 미해결 모순, 회차별 목표 충족 여부를 모아 표시.
- **작업 기록**: 생성 당시 원고 revision, 모델·프롬프트·포함 설정·초안·감수·최종 채택 기록을 연결. 사용량뿐 아니라 채택률과 수정량을 남긴다.
- **재현 가능한 실행 환경**: Windows/WSL 의존성 경로 분리, 시작 시 마이그레이션 상태 검사, 문서의 옛 ‘완료’ 기록과 현 상태 구분.

| 4 | 집필 품질 루프 | 장면 목표→초안→근거 있는 감수→수정 후보→작가 채택. 실패·부분완료를 정상완료와 구분 |
| 5 | 장편 기억 | 1/20/50/100화 시점의 고정 사건·상태 테스트에서 과거/미래 및 인물별 인지 분리. 요약 재생성 시 원고 revision 연결 |
| 6 | 독립 품질 평가 | 작가가 정한 미공개 설정 정답과 블라인드 A/B로 단일/병렬/감수 비교. 선호도·모순율·채택률·수정량·시간·비용 보고 |

**첫 개발 단위 추천:** 먼저 회차별 안전한 저장에 상세 캐시·프로젝트 전환 보호·오래된 윤문 반영 차단을 포함한다. 기존 데이터 마이그레이션과 복구 안전성을 함께 검증한 다음 AI 맥락 연결을 고친다. 이 문서는 진단과 순서 제안이며 구현을 시작하지 않는다. 후속 승인 범위는 이 첫 단위로 한정하고 6단계 전체 승인을 뜻하지 않는다.

## 7. 해석 주의

- 201개 테스트 통과는 현재 테스트 범위의 성공이다. 이 감사에서 새로 발견한 실패 경로를 검증한 것은 아니다.
- API 경계 검사 문제는 단일 사용자 로컬 앱에서도 작품 혼입·삭제 실패 문제다. 다중 사용자 인증 취약성 전체를 감사한 것은 아니다.
- 플랫폼 규정·시장 통계·장르 관례는 이번 범위에서 외부 검증하지 않았다. 기존 문서 주장을 재승인하지 않는다.
- [세부 보고서](management-review.md)의 재현 절차와 원시 로그를 수정 작업의 회귀 테스트 출발점으로 사용한다.

## 8. 핵심 목표 재평가: 시작부터 완결까지

이번 요청은 “AI 기능 추가”가 아니라 **작가가 작품을 구상하고, 연재 중 바뀌는 내용을 관리하며, 의도한 결말까지 완성하도록 지원하는 능력**으로 해석했다. 아래는 구현 승인이 아닌 고도화 제안이다.

### 8.1 이번 확인의 범위

- 기존 감사의 `source-snapshot.json`에 기록된 소스 120개의 SHA-256을 현재 파일과 비교했고 전부 일치했다. 기존 재현 기록과 현재 코드의 대응을 확인한 것이며, 테스트를 이번에 다시 실행했다는 뜻은 아니다.
- 생성·기획·설정·품질 코드와 화면을 정적으로 추가 검토했다. 운영 DB와 실제 원고는 열거나 변경하지 않았고, 실모델 집필·독자 평가는 실행하지 않았다.
- 따라서 “집필 구조상 부족한 부분”은 판단할 수 있지만, 실제 작품의 재미·상업성·완결 품질은 아직 입증되지 않았다. 기존 결함의 재현 절차와 실행 기록은 §3의 링크를 원본으로 유지한다.

### 8.3 완결 목표와 직접 충돌하는 지침 — 우선 수정 후보

이번 정적 검토에서 단순 기능 부족보다 먼저 고쳐야 할 **집필 지침 충돌**을 확인했다.

1. `backend/app/routers/ai_panel.py:49–55`의 기본 시스템 프롬프트는 “갈등을 다 풀지 마라. 해결은 다음 화에 남긴다”라고 요구한다. `EpisodeBrief`도 `next_hook`이 필수다(`schemas.py:298–313`). 최종화에서도 이 기본 지침을 구분 없이 쓰므로, 사용자가 요구한 완결·해소와 충돌할 수 있다. **일반 연재화/권말/최종화의 목적을 구분**하고, 최종화에서는 해소·여운·인물의 최종 선택을 기준으로 생성·감수해야 한다. 실제 모델이 항상 완결에 실패한다는 주장은 아니다.
2. 복선 생성 지침은 결론을 미리 풀지 말라고 하고(`ai_panel.py:275–287`), 모순 검사는 미회수 복선의 결론을 본문이 풀면 지적하도록 한다(`canon.py:66–79`). **이번 화에서 회수하도록 승인한 복선**을 전달하는 계약이 없어 정당한 회수를 방해할 수 있다. 회수 예정과 회수 완료를 구분하고, 이번 화의 허용된 공개·회수를 생성과 검사에 함께 전달해야 한다.
3. 관계의 긴장·변화는 저장하지만, 일반 생성과 모순 검사에서 `Relationship`을 조회하지 않는다(`ai_panel.py:244–254`, `canon.py:46–58`). 인물 카드에 같은 정보가 적혀 있지 않으면 중요한 관계 맥락이 빠질 수 있다. **관계 관리 화면의 내용이 실제 집필 맥락으로 이어지도록 연결**해야 한다.

이 세 가지는 새로운 모델이나 거대한 기억 시스템을 도입하기 전에 바로잡을 수 있는 범위다. 먼저 원고 보호와 회차 맥락 연결을 고친 뒤, 일반 연재화/최종화·회수 허용·관계 포함 여부를 고정 테스트로 검증한다.

### 8.4 가장 가치가 큰 고도화 5개

**1. 회차 시점별 작품 기억**

현재 `ai_panel.py:219–228`은 직전 회차 끝 2,000자를, `canon.py:35–44`는 1,000자를 참고한다. 과거 전체의 사건·상태를 대체하는 기억은 아니다. 복선 주입은 현재 상태와 생성 순서에 의존한다(`ai_panel.py:275–289`).

- 변하지 않는 설정과 변하는 상태를 분리한다. 예: 능력의 규칙 / 현재 능력 단계·부상·소지품·위치.
- 작가가 아는 사실, 독자에게 공개된 사실, 인물별로 아는 사실을 분리한다.
- 각 사실에 근거 회차·구절·원고 버전과 적용 시점을 연결한다. AI 추출 후보는 승인 전 확정 설정으로 쓰지 않는다.
- 과거 원고 수정 시 관련 요약·설정을 “재검토 필요”로 표시한다. 자동으로 과거 사실을 덮어쓰지 않는다.
- 미래 계획은 생성자가 참고할 수 있어도 현재 사실이나 인물의 지식으로 취급하지 않게 구분한다. 모든 미래 정보를 무조건 빼는 방식도 피한다.

**2. 완결에서 거꾸로 연결하는 기획**

현재 인물 생성에는 목표·결핍·비밀·변화 방향이 이미 있다(`bootstrap.py:155–181`). 부족한 것은 인물의 깊이를 요구하는 문구가 아니라 **그 변화가 어느 사건을 통해 실제로 일어났는지의 추적**이다.

- 주인공의 최종 선택과 대가, 핵심 갈등의 해결 조건, 주요 관계의 도착점을 기획서에 둔다.
- 결말 후보는 잠글 수 있지만 변경 가능하게 한다. 변경 시 영향을 받는 복선과 에피소드를 보여준다.
- 가까운 회차는 상세하게, 먼 전개는 큰 사건과 회수 조건 중심으로 관리한다. 수백 화를 처음부터 고정 생성하는 기능보다 계획 수정 지원을 우선한다.
- 최종화는 다음 화 후크를 요구하는 일반 회차와 다르게 평가한다. 여운·핵심 갈등 해결·약속 이행을 살핀다.

**3. 근거를 보여주는 회차 집필·퇴고 루프**

`EpisodeBrief`의 장점을 살려 **회차 목표 확정 → 필요한 기억 확인 → 장면 초안 → 근거 있는 감수 → 선택 수정 → 작가 확정 → 기억 갱신 후보**로 연결한다.

- “더 재미있게” 대신 사건의 인과관계, 인물의 선택과 대가, 감정의 변화, 설명 중복, 회차의 보상과 다음 전개를 항목별로 검토한다.
- 지적마다 원문 구절과 이유를 제공하고, 의도된 문체·여백·미해결은 작가가 유지할 수 있게 한다.
- 인과관계가 강한 장면은 순차 집필하고 독립적인 장면만 병렬화한다. 병렬 생성 수 증가를 품질 향상으로 간주하지 않는다.
- 초안·감수·수정본·작가 최종본을 동일한 회차/버전에 묶는다. 반영 대상이 바뀌면 그대로 삽입하지 않는다.

**4. 작업을 재개하고 끝낼 수 있는 작품 관리 화면**

캐릭터·설정·복선 목록 외에 작가가 “오늘 무엇을 해야 하는가”를 볼 수 있어야 한다.

- 현재 회차 목표, 마지막 확정 사건, 다음 장면, 미해결 감수 의견을 한 화면에서 확인한다.
- 복선은 단순 미언급 기간뿐 아니라 회수 예정 구간·선행 조건·연결 사건을 관리한다.
- 장면 원고와 회차 원고의 기준을 명확히 정하고 조립 시 미리보기·버전 확인·되돌리기를 제공한다.
- 회차의 초고/퇴고/확정 상태와 실제 연재 여부를 분리한다. 비축 원고와 전체 완결 진행도는 별도로 본다.
- 자동저장은 버전 관리나 백업과 다르다. 원고 이력·삭제 복구·복원 검증은 기본 보호층으로 둔다.

**5. 소설 품질을 실제로 검증하는 평가**

현재 품질 점수는 표면적인 문체 규칙의 충족도에 가깝다(§4.A). 독립된 품질 평가가 있기 전에는 종합 완성도 점수로 제시하지 않는 것이 맞다.

- 먼저 같은 짧은 에피소드 묶음을 현재 방식과 개선 방식으로 시작부터 작은 결말까지 집필한다. 작가가 생성 조건과 별도로 고정한 사건·설정 기준을 사용한다.
- 비교 시 모델·분량·입력 조건을 맞추고 시간·비용 차이를 기록한다. 평가자는 어느 방식의 결과인지 모르게 읽는다.
- 재미·인물 고유성·인과관계·감정 변화·회수 만족도는 사람 판단으로, 설정 모순은 출처 있는 사실 기준으로 평가한다. 동일 모델의 자기 감수는 보조 의견이다.
- 장편 원고가 확보되면 별도 단계에서 1/20/50/100화 시점의 정보 회수·미래 사실 혼입을 시험한다. 초기의 짧은 비교 시험과 구분하며, 인위적 상태 테스트의 성공을 장편 전체의 문학적 성공으로 확대하지 않는다.
- 작가 채택 여부·수정 시간·반복 수정 원인도 기록한다. 짧은 시험에서 나아졌다고 장기 연재 품질이 입증됐다고 하지 않는다. 합격 기준은 구현 전에 작가와 확정한다.

### 8.5 실행 우선순위

**의존성 순서:** 원고 보호 → AI 맥락 정상화 → 시점별 작품 기억 → 기획·집필·퇴고·완결 흐름 연결. 품질 기준과 비교 샘플은 초기부터 준비해 각 단계에 적용한다. 아래 완료 판정은 검증 관점의 초안이며, 구현 전 상세 설계에서 시험 데이터·수치 기준·대상 범위를 확정한다.

| 순서 | 개발 단위 | 완료 판정의 핵심 |
|---|---|---|
| 1 | 안전한 저장·수정 반영 | 빠른 회차/작품 전환, 저장 중 타이핑, 오래된 윤문 반영에서 최신 원고 보존. 데이터 있는 DB 업그레이드와 백업 복원 검증 |
| 2 | 공통 AI 맥락 구성·집필 지침 정합성 | 단일/병렬 요청의 회차·문체·기획·관계·설정이 일치. 실제 포함/제외 맥락 확인. 미래 계획과 현재 사실, 일반 연재화/최종화, 이번 화의 허용된 복선 회수를 구분 |
| 3 | 작품 기억과 변경 영향 추적 | 승인된 사실에 근거와 시점이 있고, 과거 수정 시 영향을 받는 기록을 식별. 인물/독자 인지 분리 시험 |
| 4 | 저장되는 회차 목표와 기획 연결 | 회차 재진입 시 브리프 복원. 계획 대비 실제 사건·인물 변화·대가를 근거 구절과 대조 |
| 5 | 완결 지원·구조 퇴고 | 핵심 갈등·인물 변화·주요 복선의 해결/의도적 미해결이 원고에 연결. 완결본 보존 및 재개 가능 |

**당장 늘리지 않을 것:** 프리셋 개수, 병렬 작업자 수, 모델 선택지, 외형 중심 화면 추가, 외부 서비스 연동. 먼저 기존 집필 기능이 현재 원고와 정확히 연결되도록 한다. 임베딩 도입도 시간축·근거·확정 절차의 대체재는 아니다.

**다음 승인 단위:** 1단계 원고 보호의 상세 설계 범위부터 검토한다. 이 감사의 계속 진행은 코드 수정이나 전체 로드맵 승인을 뜻하지 않으며, 구현 착수는 상세 설계 승인 후 진행한다.

검토 기록: 집필/관리 담당이 실제 소스를 각각 읽기 전용으로 확인했다. 별도 새 독자의 문서 검토에 따라 기존 실행 증거와 이번 정적 확인, 향후 시험 조건과 승인 범위를 명확히 했다. 로컬 링크가 모두 존재하고 감사 대상 소스 120개가 그대로임을 재확인했다. 문서 간 일관성은 현재 코드와 기존 감사 증거를 기준으로 점검했으며 역사적 HANDOFF의 완료 주장을 새 실행 결과로 옮기지 않았다. 외부 정책·시장성·장르 통계는 검증 범위에서 제외했다. 평가안은 모델 자기 감수와 독립 평가를 분리했고, 도구 중립성 주장은 없어 별도 이식성 검사는 생략했다.
